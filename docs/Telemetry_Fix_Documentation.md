# Исправление проблемы обработки ответов сервера на телеметрию

## 📋 Описание проблемы

### Симптомы
При отправке телеметрии контроллером серверу наблюдалось **аномальное поведение**, зависящее от времени отклика сервера:

1. **Быстрый ответ (<100 мс, например 39 мс)**:
   - Ответ сервера воспринимался как **команда**
   - Контроллер отправлял **ответ на эту "команду"**
   - Подтверждение телеметрии **НЕ обрабатывалось**

2. **Медленный ответ (>100 мс)**:
   - Ответ сервера корректно воспринимался как **подтверждение телеметрии** (TELEMETRY_DATA_OK)
   - Система работала правильно

### Временные характеристики
- **Период отправки телеметрии**: ~998.963 мс (~1 Гц)
- **Ширина импульса данных**: ~25 мс (длительность передачи телеметрии)
- **Критическая граница**: 100 мс

## 🔍 Анализ причины

### Архитектура до исправления

Система имела **два конфликтующих механизма** приёма данных на UART4:

#### 1. Механизм отправки телеметрии (`Master_Request`)
```
Отправка телеметрии
     ↓
HAL_UARTEx_ReceiveToIdle_DMA (буфер MB->Rx_Buffer)
     ↓
Ожидание с таймаутом ~100 мс
     ↓
   [Если ответ приходит < 100 мс]
       → Получен в MB->Rx_Buffer
       → НЕ обрабатывается как TELEMETRY_DATA_OK
       → Теряется или дублируется
     
   [Если ответ > 100 мс]
       → Таймаут
       → HAL_UART_AbortReceive_IT()
       → CommandReceiver_RestartReception()
       → Ответ приходит в RX_CMD_Buffer
       → ✅ Обрабатывается корректно
```

#### 2. Механизм приёма команд (`CommandReceiver`)
```
Постоянно слушает UART4
     ↓
HAL_UARTEx_ReceiveToIdle_DMA (буфер RX_CMD_Buffer)
     ↓
Обрабатывает все входящие данные
```

### Конфликт семафоров

Оба механизма использовали **один семафор** `PR_RX_Compl_SemHandle`, что приводило к:
- **Race condition**: кто первый получит семафор
- **Потере данных**: ответ попадает не в тот буфер
- **Дублированию обработки**: один ответ может обработаться дважды

```

Сервер RX:              │      39ms
                        └──────►[═════════]

                           Ответ воспринят как команда ❌
```

## ✅ Решение

### Новая архитектура

Создана **специализированная функция** для отправки телеметрии **без ожидания ответа**:

#### `Master_SendTelemetry()`
```cpp
MB_Error_t Master_SendTelemetry(MB_Active_t *MB, int N_Bytes)
{
    // 1. Проверки Half Duplex (RS-485)
    // 2. Отправка данных через DMA
    // 3. Ожидание ТОЛЬКО завершения передачи
    // 4. НЕ ЗАПУСКАЕТ приём ответа
    // 5. Возврат управления
    
    // Ответ обработает CommandReceiver асинхронно!
}
```

### Поток данных после исправления

```
1. TX_ToServer()
       ↓
2. WriteToServer()
       ↓
3. Master_SendTelemetry()  ← НОВАЯ ФУНКЦИЯ
   • Отправка данных
   • Ожидание завершения TX
   • ВОЗВРАТ (не ждёт ответа!)
       ↓
4. CommandReceiver_RestartReception()
   • Убеждается что приём активен
       ↓
5. CommandReceiver_Task()
   • Получает ответ в RX_CMD_Buffer
   • Обрабатывает TELEMETRY_DATA_OK
   • ✅ Работает ВСЕГДА, независимо от задержки
```

### Сравнение функций

| Характеристика | `Master_Request` | `Master_SendTelemetry` |
|----------------|------------------|------------------------|
| **Назначение** | Запрос-ответ (датчики) | Отправка телеметрии |
| **Ожидание ответа** | ✅ Да (~100 мс) | ❌ Нет |
| **Запуск приёма** | ✅ Да | ❌ Нет (уже работает) |
| **Буфер ответа** | MB->Rx_Buffer | RX_CMD_Buffer (через CommandReceiver) |
| **Семафор** | Занимает PR_RX_Compl_SemHandle | НЕ использует (освобождён для CommandReceiver) |
| **Возврат** | После получения ответа | После отправки |

## 📤 Отправка лога и приём команд

### Конфликт «лог vs ответ на телеметрию» — устранён

После отправки **телеметрии** контроллер **ждёт до 100 мс** (семафор `ServerResponseReceived_SemHandle`): успевает принять DATA_OK/DATA_FALSE от сервера, и только затем снова вызывает `osMessageQueueGet` и может отправить следующий пакет (в т.ч. лог). Поэтому передача лога **не начинается** до истечения окна приёма ответа на телеметрию — конфликта между ответом сервера на телеметрию и отправкой лога **нет**.

### Отправка лога и приём команд от сервера

Во время **любой** передачи по UART4 (телеметрия ~27 мс, лог ~53 мс, ответ на команду) линия занята: контроллер в режиме TX, приём **невозможен** (RS-485 half-duplex). Поэтому:

- Если сервер в этот момент отправит **команду** (START, STOP, GET_PARAMS и т.д.), контроллер её **не примет** — байты придут в момент, когда DE в режиме передачи.
- Это общее ограничение полудуплекса, а не особенность именно лога: то же самое справедливо для передачи телеметрии или ответа на команду.

**Практика:**

- Передача лога занимает ~53 мс раз в секунду; окно, когда команда может быть потеряна, мало.
- Команды от сервера обычно не идут непрерывно; при необходимости повторная отправка команды со стороны сервера или пользователя восстанавливает управление.

**Итог:** при отправке лога **нет дополнительного** конфликта с приёмом команд по сравнению с любой другой передачей. Конфликт «не успеть принять DATA_OK/DATA_FALSE перед отправкой лога» устранён ожиданием семафора после телеметрии.

## 📝 Примечания

### RS-485 Half Duplex
Система использует **полудуплексный RS-485**, где:
- Один физический канал для TX и RX
- Переключение через пин DE (Driver Enable)
- КРИТИЧНО: нельзя передавать во время приёма

### UART4 vs UART5
- **UART4**: Связь с сервером (программирование, телеметрия, команды)
- **UART5**: Связь с датчиками ModBus

### FreeRTOS
Система использует **FreeRTOS** с:
- Семафорами для синхронизации TX/RX
- Очередями сообщений для передачи данных
- Несколькими задачами (Tasks)

## 🎯 Выводы

**Проблема была вызвана** конфликтом между синхронным ожиданием ответа в `Master_Request` и асинхронным приёмом в `CommandReceiver`.

**Решение** — разделение функций отправки:
- Для **датчиков** (UART5): `Master_Request` с ожиданием ответа
- Для **телеметрии** (UART4): `Master_SendTelemetry` без ожидания

**Архитектура теперь**:
```
Датчики (UART5):     Запрос → Ожидание → Ответ → Обработка
Телеметрия (UART4):  Отправка → (CommandReceiver получит ответ асинхронно)
Команды (UART4):     CommandReceiver → Обработка → Ответ
```
