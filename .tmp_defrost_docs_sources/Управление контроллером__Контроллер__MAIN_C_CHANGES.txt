===============================================================================
ИЗМЕНЕНИЯ В ФАЙЛЕ main.c ДЛЯ ИНТЕГРАЦИИ CommandReceiver
===============================================================================

Внесите следующие изменения в файл Core/Src/main.c:


ИЗМЕНЕНИЕ 1: Добавить включение заголовочного файла
-------------------------------------------------------
Найдите секцию:
/* USER CODE BEGIN Includes */

Должно быть:
/* USER CODE BEGIN Includes */
#include "Components/ili9341/ili9341.h"
#include "C2CPP.hpp"
/* USER CODE END Includes */


ИЗМЕНЕНИЕ 2: Объявить поток RX_From_Server
-------------------------------------------------------
Найдите место где объявлены другие потоки, например после:

osThreadId_t TX_To_ServerHandle;
const osThreadAttr_t TX_To_Server_attributes = {
  .name = "TX_To_Server",
  .stack_size = 512 * 4,
  .priority = (osPriority_t) osPriorityNormal,
};

Добавьте после него:

/* Definitions for RX_From_Server */
osThreadId_t RX_From_ServerHandle;
const osThreadAttr_t RX_From_Server_attributes = {
  .name = "RX_From_Server",
  .stack_size = 512 * 4,
  .priority = (osPriority_t) osPriorityNormal,
};


ИЗМЕНЕНИЕ 3: Создать поток в MX_FREERTOS_Init()
-------------------------------------------------------
Найдите функцию void MX_FREERTOS_Init(void) и секцию:
/* USER CODE BEGIN RTOS_THREADS */

Должно быть что-то вроде:
/* USER CODE BEGIN RTOS_THREADS */
TX_To_ServerHandle = osThreadNew(TransferToServer, NULL, &TX_To_Server_attributes);

Добавьте после создания TX_To_Server потока:

/* creation of RX_From_Server */
RX_From_ServerHandle = osThreadNew(CommandReceiver_Task_C, NULL, &RX_From_Server_attributes);

/* USER CODE END RTOS_THREADS */

ПРОВЕРКА ПРАВИЛЬНОСТИ ИНТЕГРАЦИИ
===============================================================================

После внесения изменений проверьте:

1. Проект компилируется без ошибок
2. В списке потоков FreeRTOS появился RX_From_Server
3. После запуска устройство готово принимать команды через UART4

Для проверки работы:
1. Подключитесь к UART4 через USB-UART конвертер
2. Запустите Python скрипт:
   python test_commands.py --port COM3 --baudrate 19200
3. Проверьте что команды принимаются и обрабатываются


===============================================================================
НАСТРОЙКА UART4 (если еще не настроен)
===============================================================================

Если UART4 еще не настроен для двунаправленной связи с сервером:

1. Откройте проект в STM32CubeMX (.ioc файл)
2. Настройте UART4:
   - Mode: Asynchronous
   - Baud Rate: 19200 (или как требуется)
   - Word Length: 8 Bits
   - Parity: None
   - Stop Bits: 1
3. Настройте GPIO для UART4:
   - TX: PA0 (или другой в зависимости от платы)
   - RX: PA1 (или другой в зависимости от платы)
4. Включите прерывания UART4
5. Включите DMA для UART4 TX и RX (если еще не включен)
6. Сгенерируйте код

Актуальный порядок работы

Ниже сохранено описание исследованной версии. Для текущего кода действуют следующие правила.

В рабочем режиме сервер инициирует обмен. Команда сервера имеет формат [Type][Code][DataLen][Data][CRC16], ответ контроллера — [AA 55][Type][Code][Status][DataLen][Data][CRC16]. CRC Modbus вычисляется без AA 55 и передаётся младшим байтом вперёд. Длина поля DataLen относится только к Data.

При запуске STM32 сервер запрашивает версию и группы параметров 5, 6 и 7, затем устанавливает интервал. Запрос группы 7 ограничен общим бюджетом 950 мс. После запуска сервер периодически отправляет SEND_STATE (03/08) с байтом 01. Ответ 03/08 содержит 60 байт базовой телеметрии и байт флагов. Бит 0 (смещение 60 в Data) означает, что есть события. Старый запрос без параметров получает 60 байт. Для получения флага отдельной команды нет.

Сервер отвечает на телеметрию DATA_OK или DATA_FALSE (00/01 или 00/02). В авторежиме после DATA_OK контроллер отправляет лог регулирования 00/01 с 113 байтами данных. Сервер также читает прежние варианты лога с 89, 105 и 109 байтами. Повтор неизменившейся телеметрии с ошибочной CRC сервер подтверждает DATA_OK и отбрасывает.

В RAM контроллера 16 мест общей очереди. Диагностика занимает до 12 мест, четыре места доступны кнопкам даже при заполнении диагностикой. Записываются обработанные физические СТАРТ и СТОП, первый отказ активного датчика в серии и восстановление. Переполнения считаются раздельно для кнопок и диагностики. Перезагрузка очищает очередь.

По флагу сервер читает головную запись командой GET_EVENT (03/0D) и записывает её в log.txt. После принудительной записи файла сервер отправляет ACK_EVENT (03/0E), и контроллер удаляет выданную запись. Повтор не создаёт дубликата строки благодаря идентификатору загрузки и номеру события. При наличии следующих событий сервер продолжает чтение. Флаг служебный и в WorkData не экспортируется.
