[P1 | Title] Алгоритм программы
[P2 | Heading 1] Организация и использование данных
[P3 | Normal] Данные с датчиков используются для:
[P4 | List Bullet] анализа данных, чтобы выявить тенденцию к изменению параметров и предпринять управляющие меры,
[P5 | List Bullet] отобразить текущие данные с датчиков на экране устройства,
[P6 | List Bullet] сохранить текущие данные с датчиков на удалённом компьютере.
[P7 | Normal] Все данные с датчиков организованы в класс Sensor:
[P8 | List Bullet] Time – количество секунд, прошедших со старта программы,
[P9 | List Bullet] T – температура с датчика,
[P10 | List Bullet] H – влажность с датчика.
[P11 | List Bullet] Данные с датчиков сохраняются в двумерном массиве. Измерения массива:
[P12 | List Bullet] Номер строки в массиве.
[P13 | List Bullet] Номер датчика.
[P14 | Normal] Массив данных нужен для анализа данных, чтобы выявить тенденцию к изменению параметров и предпринять управляющие меры. Глубина массива (TQ - time quantity) определена по-умолчанию 16 строками. Т.е. в массиве сохраняются только 16 последних измерений. Этого должно быть достаточно, однако, если в процессе работы выявится потребность в большем объеме данных для анализа, размер массива можно будет увеличить.
[P15 | Normal] На экран устройства не всегда выводятся данные с датчиков, поэтому сохранённые текущие данные нужны для обновления информации на экране устройства при открывании соответствующего экрана.
[P16 | Normal] Контроллер отправляет телеметрию серверу по запросу SEND_STATE. Кадры передаются отдельной задачей через очередь. Modbus RTU на UART5 используется для опроса датчиков и модуля ввода-вывода.
[P17 | Normal] С массивом данных работают функции класса Sensor:
[P18 | List Bullet] Принять данные, положить в память – PutData().
[P19 | List Bullet] Выдать данные по запросу – GetData().
[P20 | Normal] К сохраняемым данным нужно обращаться только через описанные функции.
[P21 | Normal] Данные с датчиков на запись поступают при считывании данных с датчиков. Класс определяет граничные параметры данных и гарантирует, что данные в классе соответствуют заданным критериям.
[P22 | Normal] Данные по температуре и влажности принимаются с датчиков формате int с точностью до десятых долей. Для вывода на экран нужно int перевести во float делением на 10.
[P23 | Normal] Выдача данных осуществляется функцией GetData(TimeFromStart, SensNum, Param). Функция возвращает int число, содержащее температуру или влажность в соответствии с указанными параметрами:
[P24 | List Bullet] TimeFromStart время в секундах со старта,
[P25 | List Bullet] SensNum – номер датчика,
[P26 | List Bullet] Param – параметр = 1 для счётчика времени, 2 для температуры, 3 для влажности.
[P27 | Normal] Все параметры управления организованы в структуру, определённую массивом Control.
[P28 | Normal] В структуре присутствует признак вида данных:
[P29 | List Bullet] Время получения данных,
[P30 | List Bullet] Температура,
[P31 | List Bullet] Влажность.
[P32 | Heading 1] Управление периферийными устройствами
[P33 | Normal] К периферийным устройства относятся:
[P34 | List Bullet] ТЭНы,
[P35 | List Bullet] Вентиляторы,
[P36 | List Bullet] Клапан подачи воды на форсунки,
[P37 | List Bullet] Ворота.
[P38 | Normal] Управление устройствами сводится к битовой операции – включен или выключен. Для каждого устройства выделяется один бит в регистре управления.
[P39 | Normal] Существует один регистр аппаратного управления устройствами, загружаемый в модуль ввода-вывода, битовые выходы которого непосредственно управляют реле включения устройств. Также существуют два регистра состояния управления: автоматического и ручного, состояние которых загружается в регистр аппаратного управления в зависимости от режима работы дефростера (Рисунок 1).
[P40 | Normal] Загрузка регистра аппаратного управления выполняется из регистра состояния устройств в основном цикле работы с датчиками.
[P41 | Normal] Данные из регистра аппаратного управления записываются в выходной регистр модуля ввода-вывода, к выходам которого подключены реле управления устройствами. Таким образом, одной операцией записи в выходной регистр меняются состояния всех устройств.
[P42 | Normal] Флаг состояния каждого устройства в регистрах состояния устройств изменяется битовой операцией, чтобы случайно не изменить состояние битов управления другими устройствами.
[P43 | Normal] Состояние битов регистра аппаратного управления отображается на экране состояния в контроллере устройства. Включение одного из устройств включает анимацию отображаемого на экране устройства. Номер включенного устройства отображается рядом с пиктограммой устройства.
[P44 | Heading 1] Работа с данными
[P45 | Normal] Для работы с данными создаётся задача DataProcessing. Задача обрабатывается функцией HandleDataProcessing().
[P46 | Normal] Из функции производится вызов функции DataFunc(), которая обеспечивает обработку данных.
[P47 | Normal] Текст программы работы с данными размещён в отдельном файле Data.c.
[P48 | Normal] Задача стоит в ожидании семафора потребности в работе с данными.
[P49 | Heading 1] Считывание данных с датчиков
[P50 | Normal] Данные с датчиков считываются по программному таймеру DataTimer операционной системы. Таймер настроен на 1 секунду, т.е. считывание данных с датчиков производится 1 раз в секунду.
[P51 | Normal] Обработку прерывания от таймера выполняет функция DataTimerFunc(), которая обрабатывается в задаче TmrSvc (timer service). Перегружать таймерный сервис ожиданиями приема-передачи по последовательной шине не очень хорошо, поэтому из таймерного сервиса выполняется запуск задачи ReadData, которая специально создана для работы с последовательной шиной датчиков.
[P52 | Normal] В начале обработки DataTimerFunc() зажигается красный светодиод. И устанавливается флаг FLAG_ReadData. Красный светодиод гасится через 200 мс. Функция прекращает работу до следующего вызова. Мигание светодиода сообщает о выполнении функции считывания данных.
[P53 | Normal] По флагу FLAG_ReadData запускается задача ReadData, которая выполняет функцию ReadDataFunc() опроса всех датчиков с внесением данных в массив данных класса Sensor.
[P54 | Normal] В цикле перебираются все номера датчиков, через шину ModBus последовательно с каждого датчика считывается информация.
[P55 | Normal] Данные с каждого датчика записываются в массив данных класса Sensor в строку с моментом времени Time.
[P56 | Normal] При записи данных в массив класса Sensor функция сравнивает полученные от датчика данные с переменной отображения на экране и, если есть отличие, устанавливает флаг наличия изменений и записывает новое значение в массив переменных экрана.
[P57 | Normal] По окончании считывания данных со всех датчиков задача ReadData засыпает в ожидании новой установки флага FLAG_ReadData.
[P58 | Heading 1] Вывод на экран, переменные
[P59 | Normal] На экран устройства выводятся данные с датчиков в формате числа с плавающей точкой.
[P60 | Normal] На экране визуально отображается информация о работе вентиляторов и ТЭНов.
[P61 | Normal] На экране отображается состояние вкл/выкл клапана подачи воды.
[P62 | Normal] Каждому устройству, отображаемому на экране, присвоен порядковый номер.
[P63 | Normal] Информация с данными для вывода на экран для каждого устройства записывается в массивы:
[P64 | List Bullet] Значение датчика CurrentValue. Отдельно для Т и Н.
[P65 | List Bullet] Флаг наличия изменений FlagCurrentValueChanged. Отдельно для Т и Н.
[P66 | Normal] Массивы с данными для вывода на экран и флагами изменений сохраняется в модели экрана в классе Class Model в защищённой области. Доступ к элементу массива значений возможен только в модели. Вне модели доступ к значениям переменных возможен только через функции-члены класса Model.
[P67 | Normal] Переменные определены как static, чтобы сохранять значение в течение всего времени работы программы и предоставлять доступ к значениям из любой копии объекта класса, в котором переменные определены. Инициализация static членов класса должна быть выполнена в *.cpp области, в которой определен класс.
[P68 | Normal] Функции-члены класса Model так же, как и переменные, определены как static. К static-членам класса возможен доступ без создания объекта с типом класса-владельца членов. Для доступа к static-членам класса извне класса перед именем переменной необходимо просто добавить область видимости Model::
[P69 | List Bullet] Model::CurrentValue [SensorNumber],
[P70 | List Bullet] Model::FlagCurrentValueChanged [SensorNumber].
[P71 | Normal] Доступ к значениям переменных возможен только через функции-члены класса Model:
[P72 | List Bullet] Model::setCurrentVal(int8_t SensNumber, float Val) – запись значения и установка флага изменений,
[P73 | List Bullet] float Model::getCurrentVal(int8_t SensNumber) – возврат значения переменной,
[P74 | List Bullet] Model::clearFlagCurrentValChng(int8_t SensNumber) – сброс флага изменений
[P75 | List Bullet] int8_t Model::getFlagCurrentValChng(int8_t SensNumber) – возврат текущего значения флага.
[P76 | Heading 1] Вывод на экран, алгоритм
[P77 | Normal] Значения с датчиков считываются отдельной задачей и поступают в Data.cpp (Рисунок 2).
[P78 | Normal] Data.cpp сравнивает новое значение с предыдущим, которое хранится в модели, и, если есть изменение, устанавливает флаг изменений и записывает новое значение датчика в модель.
[P79 | Normal] Модель model.cpp сохраняет значения и обеспечивает безопасный доступ к данным.
[P80 | Normal] Операционная система периодически запускает функцию Model::tick(), находящуюся в модели (model.cpp). Внутри этой функции надо прописать вызовы самописных процедур, в каждой из которых вызывается виртуальная функция, определённая в базовом классе ModelListener в modelListener.hpp. Особенностью виртуальной функции является то, что её может переопределить любой порождённый базовым классом класс. Соответственно, если в текущем ведущем (presenter) есть переопределение функции, то она будет выполнена. Если же переопределения нет, то и исполняться будет нечему.
[P81 | Normal] Таким красивым образом реализован механизм исполнения функции из модели в конкретном ведущем, в котором есть переопределение функции.
[P82 | Normal] Для каждого экрана имеется собственный ведущий, который знает, для каких датчиков организовано отображение информации на собственном экране. В каждом ведущем, где нужно отображать информацию из модели, определена функция ValUpdatePresenter(), которая переопределяет функцию ValUpdatePresenter(), описанную в modelListener.hpp.
[P83 | Normal] Ведущий каждого экрана просматривает массив с данными для вывода на экран только для «своих» устройств и, если флаг изменений установлен, запускает функцию обновления информации в представлении …view.cpp.
[P84 | Normal] После запуска функции обновления ведущий сбрасывает флаг изменений.
[P85 | Normal] Функция обновления информации на экране запускается в соответствующем экрану представлении, она отрабатывает вывод информации на экран.

[P145 | List Bullet] Температура ниже нуля представлена дополнением к двум. Если датчик выдаст 0xFF10 – это 1111 1111 0001 0000 в формате дополнения к двум, нужно инвертировать биты и прибавить единицу: 0000 0000 1110 1111 +1 = 0000 0000 1111 0000, т.е. 240 в десятичной форме. Реальная температура составляет -240/10 = -24℃.

[P173 | Heading 1] Паузы между символами и фреймами (t1.5 и t3.5)
[P174 | Normal] Одним из самых сложных аспектов реализации протокола Modbus RTU является контроль паузы между байтами и фреймами. В соответствии со спецификацией ([2], п. 2.5.1.1) передаваемые фреймы (пакеты) должны разделяться интервалом тишины определенной длительности на линии связи. В спецификации этот интервал называется «паузой между фреймами» (inter-frame delay) и обозначается как t3.5 (о расчете его длительности мы поговорим ниже). Кроме того, фрейм должен передаваться в виде непрерывной последовательности символов. Если в течение интервала времени t1.5 (в спецификации он назван «межсимвольным таймаутом» (inter-character time-out) ) не приходит новых символов, то устройство может приступать к его проверке на корректность. Если же после истечения времени t1.5 и до истечения времени t3.5 приходит хотя бы один новый символ – то данный фрейм должен считаться некорректным и не обрабатываться устройством (при этом все символы, полученные после истечения межсимвольного таймаута, также отбрасываются, и началом нового фрейма считается первый символ, полученный после выдержки паузы между фреймами).
[P175 | Normal] Под «символом» в данном случае подразумевается один байт фрейма с «обвязкой» – стартовым битом, стоповым битом и битом четности. Согласно спецификации ([2], п. 2.5.1) в протоколе Modbus RTU один байт данных передается в виде 11 бит (8 бит данных и уже упомянутые 3 служебных бита; при этом бит четности используется даже в случае отсутствия контроля четности).
[P176 | Normal] Длительность паузы между фреймами должна составлять не менее интервала времени, который требуется для передачи 3.5 символов для используемой скорости обмена. Формула расчета выглядит следующим образом: 𝑡3.5(мс)=((3.5∙11)/(скорость (бит/с)))∙1000
[P177 | Normal] Например, для скорости 9600 бит/с минимальная длительность паузы между фреймами составит ≈ 4 мс.
[P178 | Normal] Межсимвольный таймаут вычисляется аналогичным образом: 𝑡1.5(мс)=((1.5∙11)/(скорость (бит/с)))∙1000
[P179 | Normal] Если скорость обмена превышает 19200 бит/с, то спецификация рекомендует вместо формул использовать константы: 0.750 мс для t1.5 и 1.750 мс для t3.5. Это связано с тем, что на высоких скоростях обмена при расчете интервалов времени по формулам, прерывания аппаратных таймеров будут срабатывать слишком часто (например, для скорости 115200 бит/с интервал t3.5 составлял бы ≈ 0.33 мс), что может мешать выполнению других задач.

[P573 | Heading 1] Модуль ввода-вывода
[P574 | Normal] В качестве модуля ввода-вывода используем китайский модуль MBSL 16DI16RO. Это 16 изолированных цифровых входа и 16 релейных выходов до 5А каждый.
[P575 | Normal] Модуль ввода-вывода обеспечивает доступ к информации на входах и управлению выходами по шине RS485 ModBus RTU.
[P576 | Normal] Модуль рассчитан на работу от 24 В, на это напряжение рассчитаны реле выхода. Но модуль хорошо отзывается на шину ModBus и при питании от 12 В, это удобно для целей программирования модуля, т.к. питание можно подать с колодки программирования.
[P577 | Normal] Модуль на шине ModBus может получить адрес от 1 до 247. Адрес 0 используется для широковещательной передачи данных всем устройствам, а адреса 248–255 считаются зарезервированными согласно спецификации ModBus, их использование не рекомендуется.
[P578 | Normal] Наш китайский модуль не реагирует на широковещательные адреса, ни на 0х00, ни на 0хFF.
[P579 | Normal] Модуль содержит следующие типы регистров:
[P580 | Normal] Output coil registers – регистры выходных реле. Имеется 16 регистров, каждый из которых обеспечивает 1 бит информации о состоянии одного выходного реле. Регистр можно считывать и записывать.
[P581 | Normal] Input digital quantity – регистры состояния цифровых входов. Имеется 16 регистров, каждый из которых содержит 1 бит состояния одного цифрового входа.
[P582 | Normal] Holding registers – регистры хранения. Регистры хранения содержат информацию о состоянии: входов, выходов, адрес устройства на шине, скорость обмена по шине, включение бита четности при обмене по шине, установка времени для защиты от отключения шины ModBus, версия прошивки модуля.
[P583 | Normal] Каждый тип регистра имеет свой блок адресации. Адресные пространства регистров, также называемые таблицами или блоками, различны для всех типов регистров. Это значит, что значения регистров с одинаковым адресом, но разным типом, разные.
[P584 | Normal] Адресное пространство каждого блока регистров – 16 разрядов, от 0 до 65535.
[P585 | Normal] Чтобы обозначить в документации обращение к разным типам регистров используется нестандартная адресация. Признаки использования нестандартной адресации:
[P586 | List Bullet] Адреса записываются в десятичном формате.
[P587 | List Bullet] Во всех адресах пять или шесть цифр.
[P588 | List Bullet] Адреса с недискретными данными (показания датчиков и т.п.) начинаются на 30 или 40.
[P589 | Normal] В нашем случае адреса начинаются с цифры (префикса):
[P590 | List Bullet] 0 для выходных регистров,
[P591 | List Bullet] 1 для входных регистров,
[P592 | List Bullet] 4 для регистров хранения.
[P593 | Normal] При физическом обращении префикс адреса использовать не нужно, обращения к различным адресным блокам производится разными командами (функциями), обслуживающими только свой блок регистров.
[P594 | Normal] Коды функций для различных блоков регистров:
[P595 | Normal] Описание регистров Output coil registers (function code: 0x01H,0x05H, 0x0FH):
[P596 | Normal] Описание регистров Discrete input registers (function code: 0x02H):
[P597 | Normal] Описание регистров Holding registers (function codes: 0x03H, 0x06H, 0x10H)
[P598 | Normal] В текущей работе программного обеспечения дефростера будут использоваться регистры состояния оборудования, в которых каждый бит регистра состояния будет означать состояние вкл/выкл единицы оборудования. Управлять оборудованием в этом случае удобнее, передавая в модуль ввода-вывода регистр состояния целиком.
[P599 | Normal] Для работы с регистром управления реле (Output coil registers) используются команды множественного чтения (0x01H) и множественной записи (0x0FH) регистров. В этом случае при записи или чтения в/из модуля 2-х байтов данных все 16 бит будут записаны/считаны в/из 16-ти последовательных 1-битовых регистров катушек. В команде нужно будет указать начальный адрес 1-битового регистра, количество 1-битовых регистров для записи/чтения и передать/принять два байта с битовым наполнением указанных регистров.
[P600 | Normal] Формат протокола ModBus RS485.
[P601 | Normal] Команда 0x0F
[P602 | Normal] Эта команда используется для записи нескольких значений дискретного выхода DO.
[P604 | Normal] Пример записи в несколько DO с регистрами от #20 до #29 для SlaveID адреса устройства 17. Адрес регистра будет 0013 hex = 19, т.к. счет ведется с 0 адреса.
[P606 | Normal] В ответе возвращается количество записанных регистров.
[P607 | Heading 1] Работа с модулем ввода-вывода
[P608 | Normal] Модуль ввода-вывода используется так же, как и датчики температуры. Для модуля ввода-вывода создан датчик типа 4 в структуре Sensor_type[STQ] и присвоен адрес устройства в структуре Sensor_array[SQ].
[P609 | Normal] Опрос модуля ввода-вывода выполняется в едином цикле опроса датчиков. Результат опроса – два байта, считанные отдельными словами, объединяются в одно слово с типом данных uint_16t, которое записывается в переменную Model::T_CORR_sensor вместо температуры.
[P610 | Heading 1] Программирование модуля ввода-вывода
[P611 | Normal] Модуль ввода-вывода, как и датчики температуры, требует программирования адреса устройства на шине и скорости обмена по шине.
[P612 | Normal] Программирование модуля ввода-вывода проводится в окне программирования датчиков для датчика типа 4.
[P613 | Normal] Защита от отключения выхода. Когда подчиненная станция (модуль) обнаруживает, что главная станция (сервер) не отправляла данные более установленного времени, она автоматически сбрасывает выходной сигнал для защиты безопасности полевого оборудования. Функцию непрерывной защиты сети по умолчанию можно выбрать, установив время большее 1800 секунд.
[P614 | Normal] Модуль никак не реагирует на широковещательный адрес 0xFF! Поэтому для поиска нужно будет перебирать все адреса от 1 до 247. Чтобы поиск устройства происходил быстрее, считаем, что больше двух устройств ввода-вывода не понадобится, выделяем для них адреса в начале адресного пространства, начиная с адреса 02 до 03. Адрес 01 устанавливается на заводе. Сканирование проводим по адресам от 01 до 03.
[P615 | Normal] Можно сбросить модуль до заводских настроек ( адрес 01, скорость 2 (9600)) путём нажатия кнопки RESET. Кнопка расположена на плате рядом с красным светодиодом RUN. Нужно нажать и держать кнопку, включить питание, продолжать держать кнопку более 3 секунд. Индикатор RUN мигнет 3 раза с интервалом 1 секунда и загорится постоянным светом. Теперь кнопку можно отпустить. Модуль вернется к заводским настройкам после отключения питания.
[P616 | Normal] На команду чтения 0x03 независимо от количества запрошенных регистров всегда выдаёт два байта от одного регистра.
[P617 | Normal] Модуль поддерживает сообщения информирования клиента (мастера) ModBus об исключительных ситуациях (Exception). Формат возвращаемых пакетов полностью соответствует документу «ModBus Application Protocol Specification v1.1a». Сообщения об исключительных ситуациях возникают только на запросы, адресованные данному устройству с правильным значением LRC или CRC пакета.
[P618 | Normal] Когда модуль обнаруживает одну их этих ошибок, он посылает ответное сообщение, содержащее адрес, код функции, код ошибки и контрольную сумму. Для указания на то, что ответное сообщение – это уведомление об ошибке, старший бит поля кода функции устанавливается в 1.
[P619 | Normal] Запрос: 01:03:9С:43:00:02:1B:8F – запрос чтения 2-х регистров у устройства с адресом 01, начиная с регистра 9C43h (40003d).
[P620 | Normal] Ответ: 01:83:02:С0:А1 – frame contains error. Мы видим, что в ответном коде команды 03 появился установленным старший бит, модуль вернул код 83, а это признак ошибки. Код исключительной ситуации – 02. Неподдерживаемый адрес регистра.
[P621 | Normal] Коды исключительных ситуаций:
[P622 | List Bullet] 01 – неподдерживаемая команда. Возникает при запросе от устройства команды, которую устройство не поддерживает.
[P623 | List Bullet] 02 – неподдерживаемый адрес данных. Возникает только при запросе с адресом данных, которых нет в таблицах соответствия между адресами Modbus и внутренней памятью устройства.
[P624 | List Bullet] 03 – неверное количество данных. В запросе содержится значения, недопустимые для устройства. Например, запрос количества регистров более чем 120.
[P625 | Normal] При записи новых адреса и скорости в регистры модуля переключение модуля на новые параметры произойдёт только после отключения питания и включения вновь. До снятия питания модуль отвечает при обращении по старому адресу на старой скорости, но при ответе при обращении по старым параметрам, модуль передает из регистров новые параметры.
[P626 | Heading 1] Управление модулем ввода-вывода в рабочем режиме
[P627 | Normal] Значения регистра ввода (DI) модуля ввода-вывода будут сохраняться в массиве данных класса Sensor в 16-разрядном поле T (температура).
[P628 | Normal] Значения регистра вывода (DO) модуля ввода-вывода будут сохраняться в массиве данных класса Sensor в поле 16-разрядном H (влажность).
[P629 | Normal] Регистры ввода и регистры вывода у модуля ввода-вывода 16-разрядные, но значащим является только младший байт, поэтому перед записью младший и старший байты данных нужно соединить в одно 16-разрядное число.
[P630 | Normal] В общем цикле опроса датчиков выполняем три запроса к модулю ввода-вывода: сначала запись в регистр состояния выходных реле, а затем считывание входных данных и считывание данных из регистра состояния выходных реле.
[P631 | Normal] Сначала выполняем запись в регистр состояния выходных реле.
[P632 | Normal] Для считывания входных данных и данных из регистра выходных реле делаем два запроса на считывание. Считанные байты записываем в соответствующие поля массива данных класса Sensor. Входные данные – в поле T, выходные данные (управление реле) – в поле H.
[P633 | Normal] При запросе на считывание однобитовых портов устройство сначала передаёт содержимое младших разрядов, а затем – старших.
[P634 | Normal] При приёме проверяем в ответе соответствие кода команды, CRC ответа и длину. Если есть ошибка, то в текущем цикле опроса последовательно повторяем запрос к модулю ввода-вывода три раза.
[P635 | Heading 1] Программирование управления периферийными устройствами
[P636 | Normal] Регистр аппаратного управления устройствами организован в Model.hpp.

[P655 | Heading 1] Управление роллерными воротами
[P656 | Normal] Управление роллерными воротами осуществляется по двухкнопочной схеме:
[P657 | List Bullet] Вверх.
[P658 | List Bullet] Вниз.

[P707 | Heading 1] Входные сигналы на модуль ввода-вывода
[P708 | Normal] Для анализа работы дефростера с контроллером Siemens наш контроллер будет собирать данные с датчиков температуры и влажности, а также считывать сигналы управления устройствами дефростера, важными для формирования температурно-влажностной среды в камере дефростера.
[P709 | Normal] Для считывания сигналов управления применяется контроллер ввода-вывода, монтируемый в щите управления дефростером. На входы модуля ввода-вывода подаются сигналы с выходов контроллера Siemens, переключающие исполнительные реле дефростера. Входы модуля ввода-вывода – это катоды светодиодов входных оптопар, которые срабатывают при замыкании входа на землю. Даже если контроллер Siemens не подаёт напряжение на реле, ток утечки через входную оптопару модуля заставляет реле спонтанно включаться, что нарушает работу дефростера. Пришлось сделать развязку входов модуля и исполнительного реле через транзисторы по схеме дарлингтона – ULN2803.
[P710 | Normal] Микросхема ULN2803 рассчитана на работу с сигналами уровня TTL, а мы подключали сигналы с напряжением 24 В напрямую ко входам, что привело к пробою входного транзистора. Теперь подключение входов схемы ULN2803 к сигналам от исполнительных реле выполнено через последовательно включенные резисторы 20 кОм.

[P935 | Heading 1] Аварийный режим датчиков
[P936 | Normal] В процессе работы датчики могут выходить из строя по тем или иным причинам. Показания вышедших из строя датчиков нельзя использовать в расчётах алгоритма управления, им нельзя доверять, поэтому их надо исключить из участия в алгоритме и дать сообщение оператору о необходимости замены аварийного датчика.
[P937 | Normal] Контролируем уровень шума, поступающий с датчика. Если уровень шума высокий, шум обрезается по заданному значению (>1.1 град/сек) относительно среднего значения.
[P938 | Normal] Текущая Т вычисляется как среднее по буферу предшествующих обрезанных показаний датчиков. Такая Т называется отфильтрованная и используется в алгоритме управления процесса дефростации.
[P939 | Normal] Если в процессе фильтрации (усреднения по буферу T_Clamped) выясняется, что более половины измерений обрезаны, то такой датчик считается аварийным и исключается из участия в алгоритме управления. Но «сырые» значения с датчика продолжают отображаться на экране контроллера и передаваться на сервер.
[P940 | Normal] Есть регистр аварии датчиков, в него помещается аварийный датчик и взводится общий флаг аварии для информирования оператора.

[P972 | Heading 1] Переключение между управляющими контроллерами
[P973 | Normal] Заданы два режима работы: «старый» и «новый». В старом режиме дефростером управляет старый контроллер SIEMENS, а в новом – новый контроллер STM32.
[P974 | Normal] Для переключения режимов работы в контроллере используется флаг useNewWrkAlrAlgorithm.
[P975 | Normal] В "старом" режиме при useNewWrkAlrAlgorithm = 0 алгоритм автоматического управления дефростером не должен запускаться. По команде "ПУСК" только срабатывает импульсный сигнал _Wrk.
[P976 | Normal] В "новом" режиме при useNewWrkAlrAlgorithm = 1 по команде "ПУСК" работает алгоритм автоматического управления дефростером. Импульсный сигнал _Wrk не задействован.
[P977 | Normal] Опрос датчиков и ответ телеметрии на SEND_STATE остаются в обоих режимах.
[P978 | Normal] Разделил обнаружение и обработку аварий по типам. Проверки устройств, ворот и заслонки вызываются после успешного опроса модуля ввода-вывода и, где нужен тайм-аут, в секундном такте — только в новом режиме. Диагностика датчиков, включая потерю связи и признаки выпадения датчиков продукта, работает в обоих режимах.
[P979 | Normal] Обработчики также разделены: авария устройства блокирует соответствующий выход, авария ворот или заслонки останавливает активную автоматику, авария датчика исключает его из автоматического расчёта.
[P980 | Normal] Отдельно проверил останов по аварии: он проходит только при DefrostControl_IsEnabled() — новый режим, запущенная автоматика, не ручное управление.
[P981 | Normal] В старом режиме обработчики не управляют алгоритмом.
[P982 | Normal] Независимую защитную блокировку ТЭНов при неподтверждённой работе вентиляторов сохранил в обоих режимах: это не обработчик аварийного флага.
[P983 | Normal] В ProjectServerW изменил стартовую последовательность. В режиме STM32 сервер после определения версии сначала читает группы параметров 5 и 6 из контроллера и не записывает поверх них сохранённую серверную копию. Если нужно установить флаг режима, он меняется в только что считанной группе 6 с проверкой записи. В режиме Siemens сохранён прежний порядок: установка интервала, запись серверных групп, обратное чтение.
[P984 | Normal] В режиме Сименс сервер должен начать писать телеметрию в файл при установке сигнала But_Start (бит 14 входного регистра) в 1, а останавливать запись, когда сигнал But_Start=0 10 считываний подряд.
[P1066 | Normal] Актуальный порядок обмена
[P1067 | Normal] Контроллер опрашивает датчики и модуль ввода-вывода по Modbus RTU через UART5. Для каждого запроса ожидаемую длину вычисляют по функции и числу запрошенных регистров или битов. Обычно это 9 байт для двух регистров, 7 для одного регистра или 16 дискретных входов или выходов, 8 для подтверждения записи и 5 для ответа с исключением Modbus.
[P1068 | Normal] До обновления показаний контроллер проверяет состояние UART и факт приёма, границы кадра, адрес, функцию и соответствие фактической длины запросу. Для чтения проверяется ByteCount, затем CRC по фактически принятому кадру. Ответ с исключением проверяется отдельно по длине и CRC. При ошибке чтения контроллер удерживает предыдущие показания.
[P1069 | Normal] После трёх подряд ошибок приёма активный датчик переходит в Active=0. Контроллер продолжает пробные опросы. Неудачные опросы неактивного устройства не увеличивают счётчики ошибок, не попадают в минутную сводку и не создают события. Первый правильный ответ снова включает устройство. [P1070 | Normal] Минутная диагностика GET_SENSOR_DIAG (03/0A) возвращает 85 байт данных со статистикой по устройствам и снимком последнего сбоя. Счётчики периода сбрасываются при формировании ответа. Сбой активного устройства и его восстановление отдельно передаются через очередь событий с подтверждением.
[P1071 | Normal] В рабочем режиме сервер инициирует обмен. Команда сервера имеет формат [Type][Code][DataLen][Data][CRC16], ответ контроллера — [AA 55][Type][Code][Status][DataLen][Data][CRC16]. CRC Modbus вычисляется без AA 55 и передаётся младшим байтом вперёд. Длина поля DataLen относится только к Data.
[P1072 | Normal] При запуске STM32 сервер запрашивает версию и группы параметров 5, 6 и 7, затем устанавливает интервал. Запрос группы 7 ограничен общим бюджетом 950 мс. После запуска сервер периодически отправляет SEND_STATE (03/08) с байтом 01. Ответ 03/08 содержит 60 байт базовой телеметрии и байт флагов. Бит 0 (смещение 60 в Data) означает, что есть события. Старый запрос без параметров получает 60 байт. Для получения флага отдельной команды нет.
